# Claude Code 하네스로 코드 리뷰 자동화 팀 만들어 보기

> Claude Code에 "코드 리뷰해 줘"라고만 하면 그날그날 보는 관점도, 결과 형식도 달라진다. 그래서 리뷰 담당자를 넷으로 나누고, 각자 권한과 역할을 파일로 못 박는 **하네스**를 직접 구성해 봤다.

---

## 1. 하네스가 뭔지부터

하네스(harness)는 원래 말에 채우는 마구다. 말의 힘은 그대로인데 그 힘을 원하는 방향으로 쓰게 해 준다.

Claude Code에서 말은 Claude, 마구는 프로젝트의 `.claude/` 폴더다. **"누가, 무엇을 기준으로, 어떤 순서로 일하라"를 마크다운 파일로 미리 적어 두는 것.** 프로그램을 짜는 게 아니라 조직 문서를 쓰는 일에 가깝다.

```
.claude/
├── agents/   ← 담당자 소개서 (누가 일하는가)
└── skills/   ← 업무 매뉴얼, 팀장 지침 (어떻게, 어떤 순서로)
```

이번에 만든 건 코드 리뷰를 맡는 4인 팀이다.

---

## 2. 처음에 헷갈렸던 것: 예제 저장소 구조

참고한 예제 저장소를 열었을 때 첫 폴더에는 에이전트가 `static-analyzer.md` 하나뿐이었다. 나머지 담당자는 어디 갔지? 한참 찾았다.

알고 보니 저장소는 완성된 프로젝트 하나가 아니라 **진행 단계마다 찍어 둔 스냅샷 모음**이었다. 레고 설명서의 단계별 그림처럼, 다음 폴더에 가야 나머지 셋이 합류해 있고 static-analyzer는 그대로 복사되어 같이 들어 있다.

| 단계 | 하는 일 | 이 시점의 `.claude/` |
|---|---|---|
| 1 | 대표 에이전트 1명 정의 파일 뜯어보기 | agents 1개 |
| 2 | 나머지 3명 합류, 4인 팀 완성 | agents 4개 |
| 3 | 팀장(오케스트레이터) 스킬 작성 | agents 4개 + skill 1개 |
| 4 | 버그 심은 PR에 팀 적용 | 위와 동일 |

이걸 이해하고 나니 나머지가 술술 읽혔다.

## 3. 4인 리뷰 팀 구성

| 에이전트 | 모델 | 도구 | 맡은 일 | 산출물 |
|---|---|---|---|---|
| static-analyzer | haiku | Read, Grep, Glob, **Bash** | 린트·타입·복잡도·중복 등 규칙 기반 분석 | `_workspace/review/01_static.md` |
| design-reviewer | opus | Read, Grep, Glob | 책임 분리, 경계면, 의존성 방향, 명명 | `_workspace/review/02_design.md` |
| security-auditor | sonnet | Read, Grep, Glob, **Bash** | OWASP Top 10, 시크릿 노출, 의존성 취약점 | `_workspace/review/03_security.md` |
| refactorer | opus | Read, Grep, Glob, **Edit** | 앞 세 보고서를 종합해 수정안(patch) 생성 | `_workspace/review/04_refactor.md` + `_workspace/patches/*.diff` |

표를 만들어 놓고 보니 설계 의도가 두 가지로 보였다.

### 3-1. 모델 차등: 일의 난이도에 맞춰 급을 나눈다

도구 출력을 옮기는 기계적인 일은 가벼운 haiku, 보안 판단은 sonnet, 두 파일을 교차해 설계를 따지거나 상충하는 의견을 조율해 수정안을 만드는 깊은 판단은 opus. 비용과 품질을 담당자 단위로 조절하는 구조다.

### 3-2. 권한 차등: `tools` 한 줄로 행동을 물리적으로 막는다

- **Bash**는 분석 도구를 실제로 돌려야 하는 static-analyzer, security-auditor만 받는다.
- **design-reviewer는 Bash조차 없다.** 오직 읽고 판단한다.
- **Edit은 refactorer만** 받는다. 그것도 `_workspace/patches/*.diff`만 고치도록 본문에서 한정한다.
- **아무도 git 권한이 없다.** 자동 커밋은 구조적으로 불가능하다.

"리뷰어는 코드를 고치지 마라"를 부탁하는 게 아니라 아예 도구를 안 줘서 못 하게 만든다. 고객사 서버 계정에 최소 권한만 주는 것과 똑같은 원리라 바로 와닿았다.

## 4. 에이전트 파일은 같은 뼈대에 칸만 갈아끼운다

네 파일을 나란히 펼쳐 보니 생김새가 전부 같았다. 양식 하나만 이해하면 나머지는 칸 속 내용만 읽으면 된다.

```markdown
---
name:        # 담당자 이름 (호출할 때 쓰는 식별자)
description: # 무엇을 하는지 + 트리거 키워드 (언제 불러야 하는지)
model:       # haiku / sonnet / opus
tools:       # 쓸 수 있는 도구 목록 (권한)
---

# 핵심 역할           ← 한 문장 정체성과 범위
## 작업 원칙          ← 판단 기준
## 입출력             ← 무엇을 받아서 어디에 어떤 형식으로 내놓는가
## 팀 통신 프로토콜    ← 누구에게 받고 누구에게 넘기는가
## 에러 핸들링         ← 도구나 입력이 없을 때 어떻게 하는가
## 자체 검증 체크리스트 ← 제출 전 셀프 점검
# 경계                ← 절대 하지 않는 일
```

칸마다 왜 있는지 정리해 봤다.

- **description**: 사람이 아니라 Claude가 읽는다. 메인 세션은 이 설명과 트리거 키워드("보안 감사", "취약점" 등)를 보고 일을 누구에게 맡길지 고른다.
- **작업 원칙**: 판단이 매번 흔들리지 않게 고정한다. static-analyzer는 "추론보다 도구 출력을 신뢰한다", "확신 없으면 P2로 낮춘다"가 원칙이다.
- **입출력**: 출력 경로와 형식을 못 박아야 다음 사람이 받아서 합칠 수 있다. 넷 다 P0/P1/P2 등급, 파일·라인, 근거, 권장 형식을 쓴다.
- **에러 핸들링**: "도구가 없으면 지어내지 말고 '도구 부재'라고 적어라." 조용히 틀리는 걸 막는 칸이다.
- **자체 검증 체크리스트**: "모든 발견에 파일·행 번호가 있는가", "Edit·Write 호출 0건인가" 같은 제출 전 점검.
- **경계**: 마지막에 굵게 한 번 더. "코드를 편집하지 않는다."

## 5. 담당자별 관전 포인트

### static-analyzer — 사실을 깔아 주는 담당

`tsc --noEmit`, `eslint`, `npm run lint`의 원본 출력을 근거로 인용한다. PR diff에 포함된 파일·라인만 보고 범위를 넓히지 않는다. 수정 아이디어가 떠올라도 직접 고치지 않고 refactorer에게 넘긴다.

### security-auditor — 근거 번호를 붙이는 감사관

모든 발견에 CWE 번호를 붙인다(SQL 인젝션 = CWE-89). `npm audit`, `semgrep`을 쓰되 semgrep이 없으면 시크릿 패턴 정규식 Grep으로 대체하고 "도구 부재"를 명시한다. 네트워크가 막혀 npm audit이 실패하면 "오프라인 — 의존성 취약점 미확인"으로 적는다. 폐쇄망 고객사 환경을 생각하면 꼭 필요한 처리다.

### design-reviewer — 두 파일을 동시에 보는 설계 검토자

핵심은 **"두 파일 동시 읽기"**다. API 핸들러와 그걸 호출하는 훅을 같이 열어 계약이 맞는지 본다. 파일 하나만 보면 절대 안 보이는 버그가 있어서다. 점검 기준은 **경계면 7패턴**.

1. 응답 래핑 불일치 (`{ user }` vs `user`)
2. 케이스 변환 불일치 (`user_id` ↔ `userId`)
3. 파일 경로 ↔ 링크 변환 누락
4. 상태 전이 누락 (loading / error / success)
5. API ↔ 훅 매핑
6. 즉시 응답 ↔ 비동기 (동기인 줄 알았는데 Promise 반환)
7. 옵셔널 필드 처리 (`?:`인데 직접 접근)

### refactorer — 유일하게 손대는 담당, 그래서 제약도 가장 많다

- 앞 세 보고서를 종합해 **P0에만** patch를 만든다. P1·P2는 "다음 PR 권고"로 글만 남긴다.
- 리뷰어끼리 의견이 충돌하면 trade-off를 한 줄로 적고 한쪽을 고른다.
- **생성-검증 루프 3회 상한**: patch를 만들면 리뷰어가 재검증, 거절당하면 최대 2회 재시도, 3회째도 거절이면 사람에게 넘긴다.
- 앞 보고서가 하나라도 없으면 추측으로 patch를 만들지 않는다.

## 6. 팀장: code-review-team 스킬의 6 Phase

네 명을 지휘하는 팀장은 `.claude/skills/code-review-team/SKILL.md`로 만든다. 팀장이 에이전트가 아니라 스킬인 게 처음엔 이상했는데, 다른 에이전트를 부르고 팀을 꾸리는 일은 메인 세션이 해야 하기 때문이다. 메인 세션이 이 스킬을 읽는 순간 팀장이 된다.

| Phase | 하는 일 |
|---|---|
| 0. 입력 수집 | `gh pr diff`로 PR diff를 받아 `_workspace/input/pr-{N}.diff`에 저장 |
| 1. 팀 생성 | TeamCreate로 팀을 만들고 4명 합류 (worktree로 작업 공간 격리) |
| 2. 작업 배정 | TaskCreate로 작업 4개 생성. 리팩토링은 앞 3개에 `depends_on` |
| 3. 팬아웃 | 리뷰어 3명 병렬 실행. 서로 SendMessage로 교차 발견 공유 (리더 미경유) |
| 4. 생성-검증 루프 | refactorer가 patch 생성, 리뷰어 재검증, 최대 3회 |
| 5. 통합·게시·정리 | 보고서 4개를 P0→P1→P2 순으로 합쳐 `review_report.md` 작성, PR 코멘트 게시, 팀 해체 (`_workspace/`는 보존) |

원칙 세 가지가 인상적이었다.

- **리더 무발화**: 팀장은 부르고 모으기만 한다. 리뷰 내용은 전부 워커가 쓴다.
- **자동 커밋 금지**: PR 코멘트까지만. 커밋·머지는 안 한다.
- **workspace 보존**: 팀은 해체해도 중간 보고서는 남겨 사람이 다시 볼 수 있게 한다.

주의할 점도 있다. 예제의 SKILL.md에서 `parseDiff`, `waitForTeamCompletion`, `mergeReports`, `$` 네 가지는 **실제 도구가 아니라 의사 함수**다. 그대로 복사해 쓰려면 이 부분은 직접 구현해야 한다.

## 7. 버그를 심은 PR로 시험하기

팀이 제 역할을 하는지 보려면 정답지가 있는 코드가 필요하다. 예제에서는 JWT 리프레시 기능 PR에 버그 4종을 일부러 심는다.

| 버그 | 주로 잡아야 할 담당 |
|---|---|
| SQL 인젝션 | security-auditor |
| N+1 쿼리 | 여러 담당 (교차 발견) |
| 경계면 불일치 (API는 객체를 주는데 훅은 배열 기대) | design-reviewer |
| 테스트 0건 | static-analyzer / refactorer |

볼 포인트는 각 담당자가 자기 몫을 잡는지, 그리고 남의 영역을 침범하지 않는지다. 특히 경계면 불일치는 파일 하나만 보는 리뷰로는 놓치기 쉬워서 design-reviewer의 존재 이유가 드러나는 버그다.

## 8. 실제 프로젝트에 돌려 보기

예제 저장소에는 `.claude/` 정의 파일과 문서만 있고 **리뷰 대상 코드와 결과 파일은 없었다.** 그래서 내가 만들고 있던 테스트 자동화 도구 `D:\common_tester`(Python API + React 화면 + Playwright, 약 2,500줄)를 리뷰 대상으로 삼았다.

### 8-1. 첫 번째 삽질: 다른 드라이브 폴더 붙이기

하네스 폴더에서 Claude Code를 켠 상태로 `claude --add-dir /d/common_tester`를 입력했는데 아무 일도 안 일어났다. 이건 **새 세션을 시작할 때 터미널에서 쓰는 옵션**이라, 이미 열린 세션의 입력창에 치면 그냥 대화 글로 취급된다.

```bash
# 터미널에서 새로 시작할 때
cd 하네스_폴더
claude --add-dir /d/common_tester
```

```
# 이미 열린 세션 안에서는 슬래시 명령으로
/add-dir D:/common_tester
```

### 8-2. 1차 리뷰: 한 줄로 시켰더니 알아서 병렬로 돌았다

폴더를 붙이고 이렇게만 입력했다.

```
에이전트를 이용해서 해당 프로젝트를 리뷰해줘
```

메인 세션이 리뷰 범위를 먼저 훑어서(이전 버전 스냅샷 폴더는 알아서 제외) static-analyzer, design-reviewer, security-auditor **세 명을 백그라운드로 동시에** 띄웠다. 각자 1분 남짓 걸렸고 전체는 3분 정도. 결과를 모아 우선순위별로 정리해 줬다.

| 등급 | 건수 | 대표 내용 |
|---|---|---|
| P0 | 1 | LLM이 생성한 테스트 코드를 격리 없이 서버 권한으로 실행 |
| P1 | 4 | 대상 URL 검증 부족(SSRF), API 인증 없음, 같은 판정 로직이 두 곳에서 다르게 동작, 실행 폴더 경로를 여러 모듈이 각자 조립 |
| P2 | 8 | 부분 문자열 비교로 인한 오탐, 조회(GET) 요청이 파일을 씀, 제품 전용 규칙이 범용 코드에 박힘 등 |
| P3 | 8 | `shell=True` 사용, 안 쓰는 함수, README 링크 오류 등 |

인상적이었던 건 메인 세션이 **리뷰어 보고서를 그대로 믿지 않고 핵심 지적을 코드로 다시 읽어 교차 확인**했다는 점이다. 그리고 static-analyzer의 지적 두 개를 걸러냈다.

- "이런 OpenAI 모델명은 존재하지 않는다" → 도구 근거 없이 모델의 오래된 지식으로 판단한 것이라 보류
- "UUID 충돌 위험" → 확률상 무의미하다고 기각

static-analyzer는 `model: haiku`로 지정되어 있었는데, 셋 중 보고서가 유독 얕았다. 정의 파일의 "도구 우선, 추론보다 도구 출력 신뢰" 원칙과 달리 도구를 거의 안 돌리고 추론으로 채운 결과였다. **싼 모델에 맡길수록 원칙이 지켜지는지 검증하는 단계가 꼭 필요하다**는 걸 체감했다.

### 8-3. 두 번째 삽질: 세션 중에 폴더를 옮기면 에이전트가 사라진다

정리하려고 하네스 파일들을 `harness/code-review/` 아래로 옮겼더니, 그 세션에서는 리뷰 에이전트를 더 이상 부를 수 없게 됐다. **에이전트 정의는 세션 시작 시점에 읽어 들이기** 때문이다. 옮긴 위치에서 새 세션을 열어야 한다.

```bash
cd 하네스_폴더/code-review
claude --add-dir /d/common_tester
```

### 8-4. 2차 리뷰: 이번엔 도구를 실제로 돌렸다

같은 세션에서 "다시 한 번 리뷰해봐"라고 하자, 메인 세션은 커스텀 에이전트를 못 부르는 대신 **일반 에이전트에게 각 정의 파일 내용을 그대로 읽혀 같은 역할을 맡기는** 우회로를 택했다. PR diff가 없으니 리뷰 대상 파일 목록(`_workspace/input/scope.md`)을 만들어 입력으로 넘겼고, 보고서는 정의대로 `_workspace/review/01~03_*.md`에 저장했다.

이번 결과는 정의 파일의 칸들이 실제로 작동하는 게 눈에 보였다.

- **static-analyzer**: `py_compile`, `tsc --noEmit`을 실제로 돌려 둘 다 통과. eslint와 pyflakes는 설치가 안 되어 있어 **"도구 부재"로 정직하게 표기**했다. 에러 핸들링 칸이 그대로 작동한 것이다. 1차 때의 근거 없는 지적도 사라졌다.
- **security-auditor**: `npm audit`을 돌려 의존성 취약점 0건 확인. pip-audit과 semgrep은 없어서 "도구 부재"로 적고, 정의대로 정규식 Grep과 코드 읽기로 대체했다. 모든 발견에 CWE 번호가 붙었고, 이상 없음을 확인한 항목도 "거짓 양성 방지용 기록"으로 따로 남겼다.
- **design-reviewer**: P1 3건, P2 11건. 1차 때보다 깊었다. 특히 **두 파일 동시 읽기**로만 잡히는 문제를 찾아냈다. 실행 엔진, 결과 집계, 화면 세 곳에서 같은 `failed`라는 이름이 서로 다른 의미로 쓰여서 한 화면에 "0 실패"와 "1개 실패"가 동시에 뜰 수 있다는 것, 그리고 건너뛴(skipped) 테스트가 통과(passed)로 집계될 수 있다는 상태 전이 누락. 메인 세션이 후자를 코드로 직접 확인해 사실로 판정했다.
- 보고서마다 `[cross:design]`, `[cross:static]` 같은 **교차 도메인 태그**가 붙었다. 팀 모드가 아니라 실제 SendMessage는 오가지 않았지만, 정의 파일의 "팀 통신 프로토콜" 칸이 다른 담당자에게 넘길 거리를 표시하는 형태로 나타났다.

### 8-5. 가장 큰 배움: 권한 제한은 "정식 등록"됐을 때만 작동한다

2차 리뷰에서 static-analyzer가 `01_static.md`를 **스스로 파일로 써 버렸다.** 정의 파일의 `tools`에는 Write가 없는데도.

이유는 8-4의 우회로에 있었다. 커스텀 에이전트로 정식 로드된 게 아니라 일반 에이전트가 정의 파일을 **글로 읽고 흉내만 낸** 것이라, `tools` 줄이 실제 권한 제한으로 적용되지 않은 것이다. 본문의 "Write 금지"는 그저 부탁이 되어 버렸다.

앞에서 정리한 "권한은 지시가 아니라 도구 제한으로 막는다"는 원칙을 반대 방향에서 확인한 셈이다. **`tools` 제한이 힘을 가지려면 에이전트가 `.claude/agents/`에서 정식으로 로드되어야 하고, 그러려면 정의 파일이 있는 위치에서 세션을 새로 열어야 한다.**

### 8-6. 기타 팁

- 리뷰어들은 정의대로 **코드를 한 줄도 고치지 않았다.** 보고서만 냈다.
- 대화 기록은 Claude Code에서 `/export`로 텍스트 파일로 내보낼 수 있다. 다만 리뷰 대화에는 프로젝트 경로와 취약점 내용이 그대로 들어 있으니 외부 공유 전에 꼭 훑어봐야 한다.
- refactorer 단계(P0 patch 생성)는 이번 글을 쓰는 시점에 아직 진행 중이었다. 결과는 다음 글에서 정리할 예정이다.

## 9. 정리

1. **하네스는 조직 설계다.** 한 명에게 다 시키지 않고 관점별로 담당자를 나눈다. 정적 분석, 설계, 보안, 수정.
2. **에이전트 파일은 같은 뼈대에 칸만 갈아끼운다.** 하나를 제대로 이해하면 나머지는 읽힌다.
3. **model과 tools 두 줄이 담당자의 급과 권한을 정한다.** 권한은 지시가 아니라 도구 제한으로 막는다.
4. **팀장은 부르고, 기다리고, 모으기만 한다.** 순서(depends_on), 병렬(팬아웃), 반복 상한(3회), 결과 보존까지가 팀장의 일이다.
5. **실패를 드러내게 설계한다.** 도구 부재 표기, 추측 금지, 애매하면 P2. 조용히 틀리는 게 가장 위험하다.
6. **권한 제한은 정식 로드돼야 힘을 갖는다.** 정의 파일을 글로 읽혀 흉내 내게 하면 `tools` 제한은 부탁으로 전락한다. 정의 파일 위치에서 세션을 새로 열자.
7. **싼 모델일수록 검증 단계가 필요하다.** haiku 담당자는 원칙을 건너뛰기 쉬웠고, 메인 세션의 교차 확인이 그걸 걸러 줬다.

다음엔 refactorer의 patch 결과를 확인하고, static-analyzer 모델을 올렸을 때 보고서가 얼마나 달라지는지 비교해 볼 생각이다.
