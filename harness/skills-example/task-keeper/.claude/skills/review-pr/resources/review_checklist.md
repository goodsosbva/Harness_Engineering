# PR Review Checklist

## 0. 메타데이터

- [ ] 제목이 커밋 컨벤션(`<type>(<scope>): <subject>`)을 따르는가
- [ ] 본문에 변경 이유와 내용이 설명되어 있는가
- [ ] 연결된 이슈가 있고, PR이 그 이슈를 실제로 해결하는가
- [ ] PR 범위가 하나의 목적에 집중되어 있는가 (관계없는 변경이 섞여 있지 않은가)
- [ ] CI 체크가 통과했는가

## 1. 코드 품질

- [ ] 로직이 의도대로 동작하는가 (경계값, 빈 입력, None 처리)
- [ ] 바뀐 함수를 쓰는 다른 호출부가 깨지지 않는가
- [ ] 저장소에 이미 있는 헬퍼나 패턴을 다시 구현하지 않았는가
- [ ] 쓰이지 않는 코드, 디버그 출력, 주석 처리된 코드가 남아 있지 않은가
- [ ] 이름이 역할을 잘 드러내는가
- [ ] 불필요한 추상화나 과한 설계가 없는가
- [ ] 에러 처리가 적절한가 (예외를 삼키지 않는가, 적절한 HTTP 상태 코드를 쓰는가)

## 2. 보안

- [ ] 사용자 입력을 검증하는가 (스키마 검증, 길이·형식 제한)
- [ ] SQL을 문자열로 조합하지 않는가 (ORM 또는 바인딩 파라미터 사용)
- [ ] 비밀번호, 토큰, API 키가 코드나 로그에 노출되지 않는가
- [ ] 인증·인가가 필요한 엔드포인트에 검사가 있는가
- [ ] 응답에 내부 정보(스택 트레이스, 내부 ID 등)가 새지 않는가
- [ ] 새로 추가한 의존성이 꼭 필요하고 신뢰할 수 있는가

## 3. 성능

- [ ] N+1 쿼리가 없는가 (관계 접근 시 `selectinload`, `joinedload` 사용)
- [ ] 반복문 안에서 DB 쿼리나 네트워크 호출을 하지 않는가
- [ ] 목록 조회에 페이지네이션이나 개수 제한이 필요하지 않은가
- [ ] 자주 조회하는 컬럼에 인덱스가 필요하지 않은가
- [ ] 불필요하게 전체 데이터를 메모리에 올리지 않는가

## 4. 테스트

- [ ] 변경된 동작을 검증하는 테스트가 추가되었는가
- [ ] 버그 수정이라면, 수정 전 코드에서 실패하는 테스트인가
- [ ] 실패 경로(404, 잘못된 입력 등)도 테스트하는가
- [ ] 테스트가 외부 상태에 의존하지 않고 독립적으로 실행되는가
- [ ] 기존 테스트가 모두 통과하는가

# 출력 형식

```markdown
# PR #<번호> 리뷰: <제목>

## 요약

- 변경 내용: <한두 문장>
- 연결 이슈: #<번호> (해결 여부: 해결 / 부분 해결 / 미해결)
- CI: <통과 / 실패 / 없음>
- 판정: ✅ 승인 가능 / 💬 코멘트 / ❌ 변경 요청

## 지적 사항

### 🔴 Blocker

- **`<파일>:<라인>`**: <문제>
  - 근거: <왜 문제인지>
  - 제안: <어떻게 고칠지>

### 🟡 Major

- (없으면 "없음")

### 🟢 Minor

- (없으면 "없음")

## 관점별 점검 결과

| 관점 | 결과 | 메모 |
|---|---|---|
| 메타데이터 | ✅ / ⚠️ / ❌ | |
| 코드 품질 | ✅ / ⚠️ / ❌ | |
| 보안 | ✅ / ⚠️ / ❌ | |
| 성능 | ✅ / ⚠️ / ❌ | |
| 테스트 | ✅ / ⚠️ / ❌ | |

## 잘된 점

- <좋았던 부분>
```
