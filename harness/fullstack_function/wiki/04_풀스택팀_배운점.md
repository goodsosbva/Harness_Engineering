# 리뷰 팀 다음에 구현 팀을 만들며 알게 된 것: 에이전트 설계에서 워크플로 설계로

> 리뷰 팀을 만들 때는 "에이전트 한 명을 어떻게 잘 정의하는가"를 배웠다. 구현 팀을 쌓아 보니 질문이 바뀌었다. **"여러 팀을 시간 순서대로 어떻게 굴리는가."** 이번 실습에서 얻은 하네스 엔지니어링 지식은 세 가지다.
>
> 1. 패턴 4개를 Phase별로 **조합**하는 법
> 2. 경계면만 보는 boundary-verifier가 **왜 따로** 있어야 하고, **어떻게 판정해야** 하는가
> 3. feature-pm이 Phase마다 **역할을 바꾸고 팀을 갈아끼우는** 타이밍

---

## 1. 패턴은 고르는 게 아니라 Phase마다 조합한다

리뷰 팀은 패턴 하나로 충분했다. 네 명이 동시에 읽고(팬아웃) 보고서를 모으면(팬인) 끝. 리뷰라는 일이 처음부터 끝까지 같은 모양이었기 때문이다.

구현은 다르다. 요구사항을 쪼개는 일, 설계하는 일, 코드를 짜는 일, 채점하는 일은 모양이 전부 다르다. 그래서 Phase마다 "지금 이 일은 어떤 모양인가"를 묻고 거기 맞는 패턴을 꺼낸다.

| 이 일에 대한 질문 | 답이 "예"면 | 이번 팀에서 쓰인 곳 |
|---|---|---|
| 일 전체를 누가 쪼개고 책임지나? | 계층적 위임 | PM이 처음부터 끝까지 꼭대기 |
| 앞 단계 결과가 있어야 다음을 할 수 있나? | 파이프라인 | Phase 0 → 1 → 2 → 3 → 4 |
| 여러 사람이 서로 기다리지 않고 동시에 할 수 있나? | 팬아웃 & 팬인 | Phase 1 설계 3인 |
| 만든 걸 바로바로 따로 검증해야 하나? | 생성-검증 | Phase 2·3 구현 ↔ verifier |
| 독립된 판정 하나만 필요한가? | 단독 서브에이전트 | Phase 4 test-suite |

여기서 얻은 핵심은 **패턴에 층이 있다**는 것이다.

- **바깥 층(뼈대)**: 계층적 위임과 파이프라인. 기능 하나가 시작해서 끝날 때까지 전체를 감싼다.
- **안쪽 층(엔진)**: 팬아웃과 생성-검증. 특정 Phase 안에서만 돈다.

**Phase 경계가 곧 안쪽 엔진이 갈아끼워지는 지점**이다. Phase 1에서 팬아웃이 돌다가, 설계가 확정되는 순간 Phase 2로 넘어가며 생성-검증으로 바뀐다. 리뷰 팀 때는 패턴을 "하나 고르는 것"이라 생각했는데, 실제로는 **뼈대 위에 Phase별 엔진을 끼우는 설계**였다.

조합이 교과서처럼 깔끔하지만도 않다. Phase 1은 팬아웃이지만 ui-designer와 db-migrator는 서로 직접 말하지 않고 api-designer를 거친다. API가 화면과 DB 사이의 계약이라서다. 패턴은 이름표가 아니라 **일의 의존 관계를 그대로 옮긴 모양**이다.

## 2. boundary-verifier: 왜 따로 있어야 하고, 어떻게 판정해야 하나

### 2-1. 리뷰 실습에서 이미 본 장면

지난 리뷰 실습에서 design-reviewer가 잡은 가장 좋은 지적은 두 파일 사이에 있었다. 같은 `failed`라는 이름이 실행 엔진, 결과 집계, 화면에서 서로 다른 뜻으로 쓰여 한 화면에 "0 실패"와 "1개 실패"가 동시에 뜰 수 있다는 것. 파일 하나만 보면 절대 안 보이는 버그였다.

구현 팀은 이 관점을 사후 리뷰가 아니라 **만드는 도중**에 넣는다. 그럼 왜 backend-impl이나 frontend-impl이 스스로 확인하지 않고 한 명을 더 둘까.

### 2-2. 별도 에이전트여야 하는 이유

**① 경계면은 주인이 없는 땅이다.**
backend-impl은 자기 API가 설계대로면 됐다고 믿고, frontend-impl은 자기 훅이 설계대로면 됐다고 믿는다. 둘이 맞물리는지는 누구의 일도 아니다. 주인 없는 곳에는 전담자를 둔다.

**② 만든 사람이 검증하면 자기 확증이 된다.**
생성-검증은 주체가 둘이어야 성립한다. 같은 머리가 만들고 검사하면 "내가 의도한 대로 됐다"를 확인할 뿐이다.

**③ 검증자에게 손이 있으면 판정이 흐려진다.**
verifier에게 Edit이 있으면 어긋남을 보자마자 편한 쪽을 고쳐 버린다. 그러면 "누가 설계를 안 따랐는지", "설계 자체가 모순인지"가 기록되지 않고 묻힌다. 손 없이 판정만 하게 해야 고치는 사람과 기준이 분명해진다.

이 제약은 **정식 에이전트**여야만 걸린다. 리뷰 실습에서 정의 파일을 일반 에이전트에게 글로 읽혀 흉내 내게 했더니 Write 금지가 무시됐다. `tools` 제한은 에이전트 단위로만 걸린다. 구현자 안에 "검증 모드"를 넣으면 Edit을 뺄 방법이 없다.

**④ 필요한 두뇌가 다르다.**
구현자는 확정된 설계로 한 파일씩 짜니 sonnet이면 된다. verifier는 두 파일을 동시에 놓고 추론해야 해서 opus다. 모델 배정 단위도 에이전트다.

**⑤ 판정이 한 곳에 모여야 루프가 끝난다.**
같은 경계면 REDO가 2회면 사람을 부른다. 이 카운트가 의미 있으려면 판정자가 한 명이어야 한다.

### 2-3. 정의를 직접 고치며 배운 것: FIX가 기본, REDO는 예외

처음 정의 파일에는 PASS / FIX / REDO의 뜻만 나열되어 있었다. 그런데 읽다 보니 걸리는 게 있었다. **구현이 안 맞으면 구현이 잘못된 건데, 왜 설계로 되돌리는 REDO가 있지?**

따져 보니 판정의 순서가 빠져 있었다. 어긋남을 본 verifier가 "설계가 이상하네" 하고 곧장 REDO를 내면, 구현자가 설계를 안 따른 것까지 설계 탓이 된다. 그래서 boundary-verifier.md에 **판정 순서** 칸을 새로 만들었다.

1. 양쪽 구현이 맞물리는가? → 맞물리면 **PASS**
2. 안 맞물리면, 각 구현을 **자기 설계 문서와 대조**한다. 설계와 다른 쪽이 있으면 **FIX** → 그 구현자에게. **기본은 FIX다.**
3. 양쪽 다 자기 설계대로인데도 안 맞을 때만 **REDO** → api-designer에게.

| 상황 | 원인 | 판정 |
|---|---|---|
| API 설계는 `{ user, accessToken }`인데 백엔드가 `{ data: { user } }`로 짰다 | 구현이 설계를 안 따름 | **FIX** → backend-impl |
| API 설계는 객체를 주는데 UI 설계의 훅은 배열을 기대한다. 양쪽 다 자기 설계대로 짰다 | 설계 둘이 서로 모순 | **REDO** → api-designer |
| 설계에 에러 응답 형식이 없어 양쪽이 각자 다르게 짰다 | 설계 누락 | **REDO** → api-designer |

REDO가 필요한 이유는 아래 두 경우 때문이다. 설계끼리 모순이거나 설계에 내용이 없으면, 어느 쪽 구현을 고쳐도 설계 문서는 틀린 채 남는다. 그런데 Phase 4의 test-suite는 **그 설계와 요구사항을 보고** E2E를 짠다. 코드만 맞춰 두면 테스트가 엉뚱한 기준으로 실패한다. 그래서 기준(설계)부터 바로잡고, **고쳐진 설계 기준으로 다시 FIX가 나가게** 했다. REDO도 결국 구현을 맞추는 걸로 끝난다. 한 단계를 더 거칠 뿐이다.

함께 넣은 장치가 두 개 더 있다.

- 판정 메시지에 **근거** 칸: "어느 설계 문서의 어느 부분과 어떻게 다른지"를 반드시 적는다. 받는 구현자가 무엇에 맞출지 바로 알고, 나중에 판정이 옳았는지 추적할 수 있다.
- 금지 한 줄: **"설계 문서와 대조하지 않고 REDO를 내지 않는다."** 대조를 건너뛰고 재설계로 도망가는 걸 막는다.

### 2-4. 여기서 얻은 지식

리뷰 팀 때는 에이전트를 **관점**(보안, 설계, 정적 분석)으로 나눴다. 구현 팀에서 배운 건 두 가지다.

> **권한이 다르거나, 필요한 모델이 다르거나, 책임의 단위가 다르면 별도 에이전트로 뺀다.**
>
> **판정을 맡기는 에이전트에는 판정의 뜻만이 아니라 판정의 순서를 줘야 한다.**

뜻만 주면 에이전트가 그때그때 편한 판정을 고른다. 순서를 주면 같은 어긋남에 언제나 같은 판정이 나온다. 리뷰 팀 security-auditor에 심각도 **기준**을 줬던 것과 같은 원리인데, 이번엔 기준이 아니라 **결정 순서**였다.

## 3. feature-pm은 Phase마다 다른 사람이 된다

### 3-1. 리더의 역할이 고정이 아니다

리뷰 팀의 오케스트레이터는 한 가지 모드였다. 부르고, 기다리고, 모으기만 했다. feature-pm은 Phase마다 하는 일이 바뀐다.

| Phase | PM의 모드 | 하는 일 |
|---|---|---|
| 0 | **작성자** | 요구사항 json을 직접 쓴다. 이 기능의 채점표 |
| 1 | **검토자 / 문지기** | 설계 문서 3종에 `[NOTE.]`·`[BLOCKER.]`·`[Q.]` 주석, 최대 3회, 통과해야 다음으로 |
| 2·3 | **감독자** | 워커끼리 직접 대화하게 두고 중계하지 않는다. 결과와 사람 호출 신호만 받는다 |
| 4 | **호출자 / 통합자** | test-suite를 직접 불러 채점시키고, 통합 보고서를 쓰고, 팀을 해체한다 |

PM이 처음부터 끝까지 능동적이면 두 가지가 터진다. **병목**: 구현자 둘과 verifier의 모든 대화가 PM을 거치면 PM이 막힌다. **맥락 오염**: "5회 실패 후 60초 잠금" 같은 구현 세부가 PM 머릿속에 쌓여 정작 Phase 게이트 판단이 흐려진다.

그래서 PM만 할 수 있는 일(채점표 작성, 게이트 판정, 최종 채점)은 직접 하고, 워커끼리 풀 수 있는 일에서는 물러난다. 리더는 늘 같은 강도로 개입하지 않고, **단계에 따라 개입의 깊이를 조절한다.**

### 3-2. 팀은 언제 갈아끼우나

| 전환 | 팀 교체? | 이유 |
|---|---|---|
| Phase 0 → 1 | 설계 팀 생성 | 일이 "요구사항 작성"에서 "설계"로 바뀜 |
| Phase 1 → 2 | **교체** | 산출물이 문서에서 코드로 바뀜. 설계자가 남아 있으면 구현 중에도 설계를 계속 바꾸려 들고, 동시 4명 상한도 넘는다 |
| Phase 2 → 3 | **유지** | 일의 종류가 같음. 남은 FIX·REDO 정리라 쌓인 맥락을 이어 가는 게 이득 |
| Phase 3 → 4 | **해체 후 단독** | 채점은 만든 사람들과 섞이면 안 된다 |
| REDO 발생 | 팀 교체 없이 **api-designer만 재호출** | 설계 전체가 아니라 모순된 계약 부분만 부분 복귀 |

> **일의 종류가 바뀌면 팀을 바꾸고, 같은 일이 이어지면 팀을 유지한다. 교체 신호는 Phase 게이트다.**

Phase 2와 3의 구성이 같은데 굳이 나눈 이유도 여기서 이해됐다. 팀은 같아도 **목표가 다르다.** Phase 2는 만들면서 검증, Phase 3은 남은 결함을 0으로. 종료 조건이 다르니 단계를 나눈다.

REDO가 팀 교체 없이 api-designer 한 명만 다시 부르는 것도 2-3절과 이어진다. REDO는 "설계 전체가 틀렸다"가 아니라 "이 경계면의 계약이 모순이다"라서, 그 부분만 고치고 바로 FIX로 돌아온다.

## 4. 리뷰 팀과 나란히 놓고 보면

| | 리뷰 팀에서 배운 것 | 구현 팀에서 새로 배운 것 |
|---|---|---|
| 설계 대상 | 에이전트 한 명 | 여러 팀이 시간 순서로 도는 워크플로 |
| 패턴 | 하나를 고른다 | 뼈대 위에 Phase별 엔진을 끼운다 |
| 에이전트 분리 기준 | 관점 | 관점 + 권한 + 모델 + 책임 단위 |
| 판정 설계 | 심각도 기준을 준다 | 판정 순서를 준다 (FIX 기본, REDO 예외) |
| 검증 시점 | 다 만든 뒤 | 만드는 도중 |
| 리더 | 한 가지 모드 | Phase마다 모드 전환 |
| 팀 | 한 번 꾸리고 끝 | 일의 종류가 바뀔 때 교체 |
| 실패 처리 | 정직한 표기 | 상한을 넘으면 멈추고 사람을 부름 |

리뷰 팀이 **한 장면을 잘 찍는 법**이었다면, 구현 팀은 **장면을 이어 붙여 영화를 만드는 법**이다. 에이전트 하나하나의 뼈대는 그대로고, 그 위에 언제 깨우고, 언제 해산시키고, 누가 어떤 순서로 판정하고, 어디서 멈추는지를 설계하는 층이 하나 더 생겼다.

## 5. 실제로 돌리며 확인할 것

- **패턴 조합**: Phase 1에서 설계 3인이 동시에 뜨고, Phase 2로 넘어가며 생성-검증으로 바뀌는지
- **verifier 판정 순서**: 어긋남마다 설계 대조를 먼저 하는지, FIX와 REDO의 비율이 어떻게 나오는지, 근거 칸이 채워지는지
- **verifier 권한**: 정말 한 줄도 고치지 않는지
- **PM 모드 전환**: Phase 2·3에서 PM이 대화에 끼어들지 않고 결과만 받는지
- **팀 교체 타이밍**: 설계 팀이 Phase 2 시작 시점에 해산되고, Phase 2→3에서는 유지되는지

결과는 다음 글에서 정리한다.
