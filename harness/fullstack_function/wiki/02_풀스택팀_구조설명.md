# Claude Code 하네스로 풀스택 기능 구현 팀 꾸리기 — 8인 팀이 로그인 기능을 만드는 구조

> 지난번엔 코드를 **읽고 지적만 하는** 리뷰 팀을 만들었다. 이번엔 한 단계 올라가서, 요구사항을 받아 설계하고 **코드를 직접 짜고**, 서로 검증하고, E2E 테스트까지 통과시키는 **풀스택 기능 구현 팀**을 구성해 본다.
> 참고 저장소: https://github.com/revfactory/harness-engineering-with-cc (`ex-12-03-team-8-agents`)

---

## 1. 리뷰 팀과 무엇이 다른가

| | 코드 리뷰 팀 | 풀스택 구현 팀 |
|---|---|---|
| 하는 일 | 있는 코드를 읽고 문제 보고 | 요구사항 → 설계 → 구현 → 검증 → 테스트 |
| 인원 | 4명 | 8명 (PM 포함) |
| 코드 수정 | 거의 안 함 (refactorer만 patch 파일) | 구현 담당 2명이 실제 코드를 쓰고 고친다 |
| 진행 | 한 번에 병렬로 돌고 끝 | 단계(Phase)를 밟으며 다음 단계로 넘어간다 |
| 사용 패턴 | 팬아웃/팬인 중심 | 패턴 4개를 겹쳐 쓴다 |

리뷰는 실수해도 보고서만 틀리지만, 구현은 실수하면 코드가 깨진다. 그래서 이번 팀은 **누가 코드를 만질 수 있는지, 누가 검증만 하는지, 언제 사람을 부르는지**가 훨씬 촘촘하게 설계되어 있다.

## 2. 무엇을 만드나: 로그인 기능 하나

예제의 목표 기능은 **로그인**이다. 사용자는 PM에게 "로그인 기능 만들어 줘" 한 마디만 던지고, 나머지는 팀이 한다.

정의 파일들에 박혀 있는 기술 스택은 이렇다.

| 영역 | 기술 |
|---|---|
| 백엔드 API | Next.js Route Handler (`app/api/auth/.../route.ts`) |
| DB | PostgreSQL + Drizzle ORM (마이그레이션 포함) |
| 프론트엔드 | Next.js 페이지 (`/login`), `useLogin` 훅, Zod 폼 검증 |
| 인증 | JWT 액세스 토큰 + HttpOnly 쿠키 리프레시 토큰 |
| 테스트 | Vitest 단위 테스트, MSW mock, E2E 시나리오 |

요구사항은 `login-001` ~ `login-005` 다섯 개로 쪼개지고, 마지막에 E2E 테스트 5건이 각 요구사항과 1:1로 대응한다. 즉 **"요구사항 5개가 테스트 5개로 증명되면 기능 완성"**이 이번 실습의 종료 조건이다.

## 3. 8인 팀 구성

| 에이전트 | 맡은 일 | model | tools | 활동 Phase |
|---|---|---|---|---|
| **feature-pm** | 요구사항 분해, Phase 할당, 팀 생성·해체, 통합 보고 | opus | TeamCreate, TaskCreate, AgentTool, SendMessage, TeamDelete, Read, Write | 0~4 전부 |
| api-designer | 엔드포인트, 응답 구조, 인증 흐름 정의 | opus | Read, Write, Grep, SendMessage | 1 |
| ui-designer | 화면 플로우, 컴포넌트 트리, 상태 머신, 폼 유효성 | opus | Read, Write, Grep, SendMessage | 1 |
| db-migrator | users·refresh_tokens 테이블, 인덱스, 마이그레이션 SQL 초안 | opus | Read, Write, Grep, SendMessage | 1 |
| backend-impl | API 코드, 단위 테스트, 마이그레이션 실행 | sonnet | Read, Write, **Edit, Bash**, SendMessage | 2·3 |
| frontend-impl | 페이지, 훅, 상태 코드, MSW mock | sonnet | Read, Write, **Edit, Bash**, SendMessage | 2·3 |
| boundary-verifier | 백엔드 ↔ 프론트 경계면 교차 검증 (PASS/FIX/REDO 판정) | opus | Read, Grep, SendMessage | 2·3 |
| test-suite | E2E 시나리오, 회귀 테스트 작성·실행 | sonnet | Read, Write, Bash | 4 |

### 3-1. 권한 설계: 표의 tools 칸이 곧 직무 분리다

- **설계 3인방(api / ui / db)은 Write만 있고 Edit이 없다.** 설계 문서는 쓰지만 코드는 못 고친다. db-migrator는 마이그레이션 SQL을 **초안으로만** 쓰고, 실제 실행은 Bash를 가진 backend-impl이 한다.
- **코드를 만지는 건 구현 2인뿐이다.** Edit과 Bash를 둘만 가진다. 빌드·테스트·마이그레이션 실행도 이 둘의 몫이다.
- **boundary-verifier는 Edit이 없다.** 정의 파일의 표현 그대로, verifier의 역할은 문제 검증이지 수정이 아니다. 문제를 찾으면 고칠 사람에게 넘기기만 한다. 판정의 책임은 verifier가, 수정의 책임은 구현자가 진다.
- **test-suite는 SendMessage가 없다.** 다른 담당자와 수다를 못 떤다. PM이 직접 불러서 시키고, 결과는 PM에게 돌려주는 것으로만 끝난다.
- **팀을 만들고 해체하는 도구는 PM만 가진다.**

### 3-2. 모델 설계: opus 5명, sonnet 3명

설계 3인과 PM은 opus다. 엔드포인트·인증·응답 스키마, 혹은 화면 트리·상태 머신·폼 검증을 **동시에** 추론해야 해서다. 반면 구현 2인은 sonnet이다. 설계가 이미 확정된 상태에서 한 번에 한 파일씩 코드를 쓰니 속도와 비용이 우선이다.

눈여겨볼 예외가 **boundary-verifier = opus**다. 검증만 하는데 왜 비싼 모델일까. 백엔드 파일과 프론트 파일을 **동시에 놓고** 맞물리는지 추론해야 하고, 판정 하나가 재설계(REDO)까지 이어질 만큼 파급이 크기 때문이다. 지난 리뷰 실습에서 haiku 담당자가 원칙을 건너뛰고 얕은 보고서를 냈던 걸 떠올리면 납득이 간다.

## 4. 워크플로: Phase 0 ~ 4

8명이 한꺼번에 움직이지 않는다. 핵심 원칙은 이것이다.

> 세션당 한 팀, Phase당 3~4개의 에이전트를 유지한다.

그래서 Phase마다 필요한 사람만 깨운다. PM을 포함해도 동시에 움직이는 인원은 **최대 4명**이다.

| 에이전트 \ Phase | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| feature-pm | ● | ● | ● | ● | ● |
| api-designer | | ● | | | |
| ui-designer | | ● | | | |
| db-migrator | | ● | | | |
| backend-impl | | | ● | ● | |
| frontend-impl | | | ● | ● | |
| boundary-verifier | | | ● | ● | |
| test-suite | | | | | ● |

### Phase 0 — 요구사항 분해 (PM 단독)

PM이 "로그인 기능 만들어 줘"를 받아 `00_requirements.json`을 쓴다. 요구사항 다섯 개(`login-001` ~ `005`)가 각각 카테고리와 테스트 단계를 갖고, **처음엔 전부 `passes: false`**로 시작한다. 이 false들을 하나씩 true로 바꾸는 게 이후 모든 Phase의 목표다.

### Phase 1 — 설계 팀: api + ui + db (+ PM)

설계 3인이 동시에 일한다. 각자 요구사항에서 자기 카테고리(backend / frontend / db)를 뽑아 설계 문서를 쓴다.

- api-designer → `01_api_design.md`
- ui-designer → `02_ui_design.md`
- db-migrator → `03_db_design.md` + `migrations/000_init.sql` 초안

이 단계의 핵심은 **설계자끼리 미리 맞추는 것**이다. 예를 들면 이런 협상이 오간다.

- api → ui: "로그인 성공 응답은 `{ user, accessToken }`, 리프레시 토큰은 HttpOnly 쿠키로 간다"
- ui → api: "폼 에러는 필드 단위 `{ errors: { email: [...], password: [...] } }`로 줄 수 있나?"
- api → db: "`users.email`에 UNIQUE 제약, 중복이면 409로 매핑하겠다"
- db → api: "`password_hash`는 bcrypt라 varchar(60), 리프레시 토큰은 별도 테이블"

정의 파일을 자세히 보면 완전한 삼각형은 아니다. **ui-designer와 db-migrator는 직접 대화하지 않고 항상 api-designer를 거친다.** API가 화면과 DB 사이의 계약 그 자체이기 때문에 api-designer가 허브 역할을 하는 구조다. PM은 산출물을 검토해 `[NOTE.]`·`[BLOCKER.]`·`[Q.]` 주석을 달고, 이 검토 사이클은 **최대 3회**다.

### Phase 2 — 구현 팀: backend + frontend + verifier (+ PM)

설계 팀은 해산하고 새 팀이 꾸려진다.

- **backend-impl**: 마이그레이션 실행 → 엔드포인트별 Route Handler 작성 → 단위 테스트(`npm test`) 통과
- **frontend-impl**: **MSW mock부터** 만든다(mock-first). 백엔드가 덜 됐어도 결정론적으로 화면을 개발할 수 있게. 그다음 `/login` 페이지, Zod 폼, `useLogin` 훅, 상태 머신(loading / idle / error / success)
- 두 구현자는 상시 대화한다. "이 엔드포인트는 5회 실패 후 60초 잠금이야", "에러 메시지 한국어로 i18n 키 줄 수 있어?" 같은 식으로.
- **boundary-verifier**: 엔드포인트가 완성되거나 훅이 작성된 직후 끼어들어 **경계면 7패턴**(응답 래핑, 케이스 변환, 파일경로↔href, 상태 전이, 훅 매핑, 동기↔비동기, 옵셔널 필드)을 검사한다. 지난 리뷰 팀 design-reviewer의 그 7패턴이 그대로 넘어왔다.

verifier의 판정은 딱 세 가지뿐이다.

| 판정 | 의미 | 누구에게 넘기나 |
|---|---|---|
| **PASS** | 맞물린다 | 다음 경계면으로 |
| **FIX** | 구현자 한 명이 고칠 수 있다 | backend-impl 또는 frontend-impl |
| **REDO** | 설계 자체가 틀렸다 | api-designer 재호출 |

### Phase 3 — 잔여 결함 수정 (Phase 2 연장)

Phase 2에서 남은 FIX·REDO를 마저 정리한다. **새 팀을 만들지 않고** 같은 3인이 계속 간다. 구성이 Phase 2와 똑같은 이유다. 같은 경계면에서 REDO가 **2번** 나오면 더 돌리지 않고 강제로 통과시킨 뒤 `manual_queue.md`에 적고 PM에게 `[MANUAL_INTERVENTION_REQUIRED]`를 올린다. 무한 재설계를 막는 차단기다.

### Phase 4 — 통합 & 테스트 (test-suite)

PM이 test-suite를 **팀이 아니라 서브에이전트로 단독 호출**한다. test-suite는 요구사항 5개마다 E2E 시나리오 1개씩 작성하고, MSW로 외부 의존을 끊은 뒤 `npm test`로 5건 통과를 확인한다. 결과는 PM에게만 돌려주고, PM이 `07_integration_summary.md`를 쓰고 팀을 해체(TeamDelete)한다. 테스트가 실패하면 test-suite는 직접 고치지 않고 PM에게 `[BLOCKER.]`만 반환한다.

## 5. 이 워크플로에 겹쳐진 패턴 4개

| 패턴 | 어디서 쓰이나 | 무엇을 해결하나 |
|---|---|---|
| **계층적 위임** | PM → Phase별 팀 → 각 담당자 | 8명을 PM 한 명이 직접 지휘하지 않고, Phase마다 팀을 만들어 일을 내려보낸다. PM은 워커끼리의 대화를 중계하지 않고 결과만 받는다. |
| **팬아웃 & 팬인** | Phase 1 설계 | api / ui / db가 동시에 설계(팬아웃)하고, 세 문서를 PM이 모아 검토(팬인)한다. |
| **파이프라인** | Phase 0 → 1 → 2 → 3 → 4 | 앞 단계 산출물이 다음 단계 입력이 된다. 요구사항 json → 설계 문서 → 코드 → 테스트. PM이 단계마다 게이트를 지킨다. |
| **생성-검증** | Phase 2·3 구현 | 구현자가 만들고(생성) verifier가 PASS/FIX/REDO로 판정(검증)하는 루프. REDO 2회 상한으로 끝이 보장된다. |

그림으로 그리면 이렇다.

```
                        사용자: "로그인 기능 만들어 줘"
                                     │
                              ┌──────▼──────┐
                              │  feature-pm │  ← 계층적 위임의 꼭대기
                              └──────┬──────┘
   ── 파이프라인 ───────────────────────────────────────────────────────▶
   Phase 0          Phase 1               Phase 2·3                Phase 4
  ┌────────┐   ┌──────────────┐   ┌────────────────────────┐   ┌────────────┐
  │요구사항 │──▶│ api ui db    │──▶│ backend ⇄ frontend     │──▶│ test-suite │
  │ 분해    │   │ (팬아웃)      │   │    ↑ FIX     ↑ FIX     │   │ (E2E 5건)  │
  │ (PM)   │   │   ↓ ↓ ↓      │   │   boundary-verifier    │   └─────┬──────┘
  └────────┘   │ PM 검토(팬인) │   │  (생성-검증 루프)        │         │
               └──────────────┘   │   REDO → api-designer  │   07_integration
                                  └────────────────────────┘     _summary.md
```

## 7. 안전장치 모음

구현 팀은 코드를 실제로 바꾸기 때문에 "언제 멈추고 사람을 부를지"가 정의 파일 곳곳에 박혀 있다.

| 상황 | 동작 |
|---|---|
| PM 검토 사이클 3회 초과 | 다음 Phase 진입 차단, 사람 호출 |
| 설계자 간 합의가 3회 이상 맴돎 | PM에게 `[BLOCKER.]` |
| 같은 경계면 REDO 2회 | 강제 PASS + `manual_queue.md` + `[MANUAL_INTERVENTION_REQUIRED]` |
| 마이그레이션 실패 | 즉시 rollback 후 `[BLOCKER.]` |
| E2E 실패 | test-suite는 고치지 않고 PM에 `[BLOCKER.]` |
| 동시 활성 5명 이상 요청 | 세션 분할 권고 |
| verifier가 PASS/FIX/REDO 외 판정 | 금지 |

공통점은 **"끝없이 돌지 않는다"**와 **"검증하는 쪽은 고치지 않는다"** 두 가지다.

## 8. 저장소에 있는 것, 내가 채워야 할 것

저장소의 풀스택 예제 폴더에 들어 있는 건 이것뿐이다.

- `.claude/agents/` 8개 정의 파일
- 팀 표, Phase 활성 매트릭스, 모델 채택 근거 문서
- CLAUDE.md (권한 강제 규칙)

**오케스트레이션 스킬도, Next.js 프로젝트도, DB도 없다.** README에도 "정적 에이전트 정의"라고 되어 있다. 그래서 이번 실습에서 직접 할 일은 이렇다.

1. 빈 Next.js 프로젝트를 만든다.
2. 8개 정의 파일을 프로젝트의 `.claude/agents/`에 놓는다.
3. 로컬 PostgreSQL을 준비한다 (backend-impl이 마이그레이션을 실제로 돌리니까).
4. 에이전트 팀 모드를 켜고, **정의 파일이 있는 위치에서 새 세션을 연다.**
5. "로그인 기능 만들어 줘"로 시작해 Phase 0 ~ 4가 어떻게 흘러가는지 지켜본다.

```bash
cd 풀스택_실습_폴더
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude
```

## 9. 실습하면서 확인해 볼 포인트

지난 리뷰 팀 실습에서 배운 것들을 바탕으로 미리 체크리스트를 만들어 뒀다.

- **권한이 진짜로 걸리는가.** 지난번엔 정의 파일을 글로 읽혀 흉내 내게 했더니 Write 금지가 무시됐다. 이번엔 반드시 `.claude/agents/`에서 정식 로드된 상태로 돌려서, boundary-verifier가 정말 코드를 못 고치는지, 설계 3인방이 정말 Edit을 못 쓰는지 확인한다.
- **PM은 누가 맡게 되는가.** feature-pm이 에이전트 정의로 되어 있지만, 팀을 만들고 다른 에이전트를 부르는 일은 메인 세션만 할 수 있었다(리뷰 팀에서 오케스트레이터가 스킬이었던 이유). 실제로 메인 세션이 PM 정의를 따라 PM 역할을 하는지 지켜본다.
- **동시 활성 4명 상한이 지켜지는가.** Phase 1에서 구현 담당이 미리 깨어나진 않는지.
- **생성-검증 루프가 실제로 끝나는가.** PASS/FIX/REDO가 몇 번 오가는지, REDO 2회 차단기가 작동하는 상황이 오는지 세어 본다.
- **`passes: false` → `true`.** 마지막에 요구사항 5개가 E2E 5건으로 전부 증명되는지가 최종 성적표다.

---

## 10. 정리

이번 실습은 한 문장으로 **"PM 한 명이 요구사항을 쪼개고, Phase마다 3명짜리 팀을 갈아 끼우며, 설계 → 구현 → 검증 → 테스트를 파이프라인으로 흘려보내 로그인 기능을 완성하는 것"**이다.

리뷰 팀에서 배운 뼈대(정의 파일 구조, tools로 권한 분리, 모델 차등, 경계면 7패턴)가 그대로 재료로 쓰이고, 그 위에 **Phase 게이트, 팀 교체, 생성-검증 루프, 사람 호출 차단기**가 새로 얹힌다. 다음 글에서는 실제로 돌린 결과를 정리할 예정이다.
