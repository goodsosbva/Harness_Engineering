# 레거시 마이그레이션 팀 하네스, 빈 폴더부터 쌓기

> 리뷰 팀은 "동시에 보고 끝내는" 팀, 구현 팀은 "Phase마다 팀을 갈아끼우는" 팀이었다. 이번엔 **같은 작은 일이 수천 번 반복되는** 일을 맡는 팀이다. 레거시 파일 3,500개를 새 방식으로 바꾸는 마이그레이션. 감독자 패턴이 주인공이다.
> 참고 저장소: https://github.com/revfactory/harness-engineering-with-cc (`ex-13-01-dependency-mapper`)
>
> 저장소에는 `dependency-mapper` 에이전트와 샘플 레거시 코드 17개만 있다. README가 언급하는 `mock-mapper.sh`, `verify.sh`는 없다. 나머지 팀원(기준선 테스트, 변환 워커, 검증, 감독자 스킬)은 4단계 워크플로에 맞춰 직접 설계했다.

## 1. 왜 감독자인가

### 단일 에이전트가 무너지는 이유
- **맥락이 넘친다.** 100번째 파일과 3,000번째 파일의 변환 방식이 달라진다.
- **중간에 끊기면 처음부터다.** 진행 상태가 머릿속에만 있다.
- **실패가 묻힌다.** 한 파일이 깨져도 다음으로 넘어간다.

### 고정 팬아웃이 무너지는 이유
- **순서가 있다.** `UserCard` → `useAuth` → `api` → `http`. 아래부터 바꿔야 위가 안 깨진다. 처음에 기계적으로 나누면 순서가 찢어진다.
- **일의 양이 고르지 않다.** 같은 개수를 나눠도 어떤 워커는 놀고 어떤 워커는 한참 걸린다.
- **실패를 다시 나눌 수 없다.**

### 감독자가 푸는 방식
감독자는 대기열을 들고 있다가, 워커가 손이 비면 **지금 시작할 수 있는 다음 일**을 하나 건넨다. 워커 입장에서는 일을 "가져가는" 구조.

| | 단일 에이전트 | 고정 팬아웃 | 감독자 |
|---|---|---|---|
| 분배 시점 | 없음 | 처음에 한 번 | 워커가 빌 때마다 |
| 의존 순서 | 머릿속 | 찢어짐 | 대기열이 지킴 |
| 일의 불균형 | 해당 없음 | 노는 워커 생김 | 자동 흡수 |
| 실패 처리 | 묻힘 | 못 옮김 | 재배정 후 상한 넘으면 사람 |
| 중단 후 재개 | 처음부터 | 어려움 | 상태 파일에서 이어서 |

## 2. 팀 구성과 워크플로

| 단계 | 담당 | 하는 일 | 패턴 |
|---|---|---|---|
| 1. 의존 매핑 | dependency-mapper | import 그래프 → 배치와 순서 | - |
| 2. 기준선 테스트 | baseline-tester | 변환 **전** 동작을 테스트로 박제 | - |
| 3. 점진 변환 | 감독자 + migration-worker 여러 명 | 시작 가능한 배치를 워커가 하나씩 가져감 | **감독자** |
| 4. 검증 | migration-verifier | 배치마다 타입 체크·기준선 테스트로 판정 | **생성-검증** |

감독자는 **스킬을 읽은 메인 세션**. 워커끼리 대화가 없으므로 에이전트 팀 모드 없이 **일반 서브에이전트로 충분**. 변환 내용은 샘플이 `.jsx`라 **JavaScript → TypeScript**로 잡았다.

### baseline-tester

```bash
cat > .claude/agents/baseline-tester.md << 'EOF'
---
name: baseline-tester
description: 마이그레이션 전에 레거시 코드의 현재 동작을 테스트로 박제한다. 변환 전 코드에서 전부 통과해야 한다. 기준선, 박제, 회귀 테스트 키워드에서 사용.
model: sonnet
tools: Read, Grep, Write, Bash
---

## 역할
- src의 export마다 현재 동작을 그대로 기록하는 테스트를 쓴다.
- 기대값은 "올바른 동작"이 아니라 "지금의 동작"이다. 버그도 그대로 박제한다.

## 입력
- src/ 전체
- batches.json (manual-queue에 들어간 파일은 제외)

## 절차
1. 파일마다 export 목록을 뽑는다.
2. 외부 호출(fetch 등)은 vi.fn으로 막고, 무엇이 어떤 인자로 호출되는지까지 기록한다.
3. tests/baseline/에 테스트 작성. import 경로에 확장자를 쓰지 않는다 (.jsx → .tsx 후에도 그대로 동작하도록).
4. npm test 실행. 레거시 코드에서 전부 통과해야 한다.

## 출력
- tests/baseline/*.test.js
- 통과 결과 요약 (파일별 테스트 수)

## 에러 핸들링
- src 파일은 읽기만 한다. Edit이 없다.
- 실행하면 문제가 생기는 동작(예: 무한 재귀)은 "그 문제가 일어난다"를 기대값으로 박제한다.
- 레거시에서 통과하지 않는 테스트는 기준선이 아니다. 통과할 때까지 테스트를 고친다.
EOF
```

### migration-worker

```bash
cat > .claude/agents/migration-worker.md << 'EOF'
---
name: migration-worker
description: 감독자에게 배치 하나를 받아 그 배치의 파일만 JavaScript에서 TypeScript로 변환한다. 여러 명이 동시에 일한다. 변환, 마이그레이션 워커 키워드에서 사용.
model: sonnet
tools: Read, Grep, Write, Edit, Bash
---

## 역할
- 받은 배치의 파일만 변환한다. 다른 배치 파일은 건드리지 않는다.
- 동작은 바꾸지 않는다. 버그도 그대로 옮긴다.

## 입력
- 배치 하나 (id, files, pattern)
- 재시도라면 이전 검증 실패 사유

## 변환 규칙
1. .jsx → .tsx (JSX가 없으면 .ts). git mv로 이름을 바꿔 이력을 남긴다.
2. 함수 인자와 반환값에 타입을 붙인다. 모르면 unknown으로 두고 any는 쓰지 않는다.
3. import 경로는 확장자 없이 유지한다.
4. 로직, 문자열, 호출 순서는 그대로 둔다.

## 절차
1. 배치 파일과, 그 파일이 import하는 이미 변환된 파일의 타입을 읽는다.
2. 변환 규칙대로 바꾼다.
3. npx tsc --noEmit으로 이 배치 파일에 오류가 없는지 확인한다.
4. 감독자에게 변환한 파일 목록과 특이사항을 돌려준다.

## 에러 핸들링
- tests/ 아래 파일은 절대 수정하지 않는다.
- 동작을 바꿔야만 타입이 맞는 경우 변환을 멈추고 감독자에게 사유를 보고한다.
- git commit 금지.
EOF
```

### migration-verifier

```bash
cat > .claude/agents/migration-verifier.md << 'EOF'
---
name: migration-verifier
description: 변환이 끝난 배치 하나를 검증해 PASS 또는 FAIL만 판정한다. 직접 고치지 않는다. 검증, 배치 검증 키워드에서 사용.
model: sonnet
tools: Read, Grep, Bash
---

## 역할
- 배치 하나가 변환 규칙을 지켰고 동작이 그대로인지 판정한다.

## 판정 순서 (반드시 이 순서로)
1. npm run typecheck — 이 배치 파일에서 타입 오류가 있으면 FAIL
2. npm test — 기준선 테스트 중 하나라도 실패하면 FAIL (동작이 바뀜)
3. git diff로 이 배치 외 파일이나 tests/가 바뀌었으면 FAIL (경계 침범)
4. any 사용, 로직 변경 흔적이 있으면 FAIL
5. 모두 통과하면 PASS

## 출력
- verdict: PASS | FAIL
- 실패 단계 번호, 파일:라인, 근거 (도구 출력 인용)

## 에러 핸들링
- Edit, Write가 없다. 직접 고치지 않는다.
- 도구 출력 없이 판정하지 않는다.
EOF
```

boundary-verifier와의 차이: 판정이 PASS/FAIL 둘뿐(되돌아갈 설계가 없고 기준은 기준선 테스트 하나), 모델은 sonnet(판단 대부분이 도구 결과로 정해짐).

## 6. 감독자 스킬

```bash
mkdir -p .claude/skills/legacy-migration
cat > .claude/skills/legacy-migration/SKILL.md << 'EOF'
---
name: legacy-migration
description: 레거시 코드 대규모 마이그레이션을 감독자 패턴으로 진행한다. "마이그레이션해 줘", "TypeScript로 바꿔 줘" 요청에서 사용.
---

# 레거시 마이그레이션 감독자

메인 세션이 감독자다. 직접 변환하지 않는다. 대기열을 관리하고 일을 나눠 주고 판정을 받는다.

## 상태 파일
- _workspace/migration/batches.json — 진행 상태의 유일한 기준. 상태가 바뀔 때마다 즉시 저장한다.
- _workspace/migration/manual-queue.md — 사람이 봐야 할 파일과 사유
- 배치 status: pending → in_progress → converted → verified | failed

## 1단계: 의존 매핑
- dependency-mapper에게 target_glob "src/**/*.jsx"를 넘긴다.
- 돌려받은 batches.json 초안을 저장한다. max_attempts가 비어 있으면 3.
- 파싱 실패 파일은 manual-queue.md에 기록한다.
- cyclic 경고가 붙은 배치를 사용자에게 알린다.

## 2단계: 기준선 테스트
- baseline-tester를 부른다.
- npm test가 레거시 코드에서 전부 통과해야 3단계로 간다. 하나라도 실패하면 멈춘다.

## 3단계: 점진 변환 (감독자 루프)
반복한다, pending 배치가 없어질 때까지:
1. 시작 가능 배치 = status가 pending이고 depends_on의 모든 배치가 verified인 것
2. 비어 있는 워커 자리(최대 3)만큼 시작 가능 배치를 꺼낸다. complexity가 높은 것부터.
3. 꺼낸 배치를 in_progress로 바꾸고 저장한 뒤 migration-worker에게 하나씩 넘긴다.
4. 워커가 돌아오면 converted로 바꾸고 4단계 검증으로 보낸다.
5. 워커 자리가 비면 바로 1로 돌아가 다음 배치를 꺼낸다. 다른 워커를 기다리지 않는다.

## 4단계: 배치별 검증 (생성-검증 루프)
- migration-verifier에게 배치를 넘긴다.
- PASS → verified로 저장. 이 배치를 기다리던 배치들이 시작 가능해진다.
- FAIL → attempts + 1
  - attempts < max_attempts: 실패 사유를 붙여 pending으로 되돌린다 (다시 대기열로)
  - attempts = max_attempts: 그 배치 파일을 git checkout으로 되돌리고 failed로 저장, manual-queue.md에 기록.
    이 배치에 의존하는 배치들도 failed로 막고 사유를 남긴다.

## 끝
- verified / failed / manual-queue 건수를 사용자에게 보고한다.
- 커밋은 하지 않는다.
EOF
```

핵심 세 줄: "다른 워커를 기다리지 않는다"(팬아웃과의 차이), 시작 조건은 converted가 아니라 **verified**, FAIL은 재배정 또는 되돌리고 의존 배치까지 차단.

```
2층              utils/api

```

| 단계 | 확인할 것 |
|---|---|
| 1. 의존 매핑 | 층 구조를 거스르지 않는가. 순환 두 파일이 한 배치 + 경고. truncated가 manual-queue로 |
| 2. 기준선 | 레거시에서 전부 통과. 순환 파일의 "스택이 터진다"가 박제되는가 |
| 3. 점진 변환 | 1층부터 나가는가. 한 워커가 끝나자마자 다음 배치가 나가는가. 남의 배치 파일을 안 건드리는가 |
| 4. 검증 | FAIL이 사유와 함께 대기열로 돌아가는가. 3회째면 되돌려지고 위 배치가 막히는가 |
| 전체 | `batches.json`만 보고 진행 상황을 알 수 있는가 |

## 10. 세 팀 비교

| | 리뷰 팀 | 구현 팀 | 마이그레이션 팀 |
|---|---|---|---|
