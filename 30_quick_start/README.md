# 30분 실습: 첫 번째 하네스

Claude Code에서 커밋 메시지 초안을 작성하고 검토하는 작은 하네스를 살펴봅니다. 이 실습의 핵심은 메시지를 잘 쓰는 프롬프트 하나가 아니라 **입력, 역할, 검토, 재시도, 종료 조건을 함께 설계하는 것**입니다.

## 실습에서 익힐 내용

- 하네스가 프롬프트와 어떻게 다른지 구분합니다.
- 작성자와 검토자 에이전트가 서로 다른 책임을 갖도록 정의합니다.
- 스킬로 여러 단계를 순서대로 연결합니다.
- diff, 초안, 검토 보고서가 같은 작업을 가리키는지 확인합니다.
- 검토가 실패했을 때 자동 통과시키지 않고 멈추는 이유를 이해합니다.

## 흐름 한눈에 보기

`스테이지된 변경` → **작성자** → `commit-draft.md` → **검토자** → `review-report.md` → **통과 또는 수정**

스킬은 이 순서를 지휘합니다. 작성자는 실제 변경을 근거로 초안을 쓰고, 검토자는 같은 변경과 초안을 대조합니다. `PASS`면 초안을 사용자에게 제시하고, `REDO`면 수정 지시를 작성자에게 되돌립니다. 이 실습은 메시지 초안까지 다루며 `git commit`은 실행하지 않습니다.

## 파일별 역할과 설계 이유

실습 프로젝트는 `my-first-harness/`입니다.

| 파일 | 맡은 일 | 왜 필요한가 |
| --- | --- | --- |
| [`CLAUDE.md`](my-first-harness/CLAUDE.md) | 공통 규칙과 산출물 위치 지정 | 작성자와 검토자가 같은 기준을 공유 |
| [작성자 에이전트](my-first-harness/.claude/agents/commit-msg-author.md) | staged diff와 최근 커밋 로그를 읽고 초안 작성 | 근거 없는 추측을 줄이고 결과 경로를 고정 |
| [검토자 에이전트](my-first-harness/.claude/agents/commit-msg-reviewer.md) | 형식, 제목 길이, diff 일치 확인 후 판정 기록 | 만든 역할과 검증하는 역할을 분리 |
| [커밋 메시지 스킬](my-first-harness/.claude/skills/commit-message/SKILL.md) | 사전 확인, 두 에이전트 호출, 재시도와 종료 처리 | 실행 순서를 반복 가능하게 유지 |
| [작업 산출물](my-first-harness/_workspace) | 초안과 검토 보고서 보관 | 다음 역할이 결과를 같은 위치에서 읽음 |

`CLAUDE.md`는 매 작업에 필요한 짧은 규칙을 둡니다. 여기서는 `type(scope): subject` 형식과 `_workspace/` 사용을 정합니다. 긴 작업 절차는 스킬에, 역할별 판단 기준은 에이전트 파일에 두어 한 파일이 모든 책임을 떠안지 않게 합니다.

### 작성자 파일에서 볼 점

작성자는 `git diff --cached`와 `git log -10 --oneline`을 입력으로 사용하고 `_workspace/commit-draft.md`에 결과를 씁니다. 제목 72자 이하, 본문 3줄 이내, diff에 없는 변경을 넣지 않는 규칙은 이 역할의 품질 계약입니다. 최근 로그가 비어 있으면 없는 스타일을 만들어내지 말고 프로젝트 규칙과 diff를 근거로 작성해야 합니다.

### 검토자 파일에서 볼 점

검토자는 같은 diff를 다시 읽고 초안에 적힌 사실을 대조합니다. 판정은 `PASS` 또는 `REDO`이고, 재작성 요청에는 고칠 위치와 이유가 있어야 합니다. 예를 들어 “범위가 틀렸다”보다 “diff에는 에이전트와 스킬이 추가됐는데 제목은 README만 설명한다”가 작성자가 바로 고칠 수 있는 피드백입니다.

### 스킬에서 볼 점

스킬은 먼저 `git diff --cached --quiet`로 스테이지된 변경을 확인합니다. 종료 코드 0은 변경 없음, 1은 변경 있음입니다. 변경이 없으면 `git add`가 필요하다고 안내하고 종료합니다. 변경이 있으면 작성자, 검토자 순으로 호출하고 판정에 따라 `PASS`는 제시, `REDO`는 재작성으로 보냅니다.

`allowed-tools`는 스킬을 호출한 턴에서 지정 도구를 미리 허용하는 설정입니다. 전체 보안 제한을 대신하지 않으므로, 사용 중인 권한 설정도 함께 확인하세요.[1]

## 30분 따라 하기

### 0~5분: 입력 준비

Git과 Claude Code가 필요합니다. 저장소 루트에서 실습 프로젝트로 이동해 상태와 staged 변경을 확인합니다.

```bash
cd 30_quick_start/my-first-harness
git status --short
git diff --cached --name-only
```

처음에는 staged 변경이 없을 수 있습니다. `my-first-harness/`에 **새 파일** 하나를 만들고 한 줄을 적은 뒤 스테이지하세요. 예를 들어 `practice.txt`를 사용할 수 있습니다. 이미 같은 이름의 파일이 있다면 다른 이름을 정해 아래 명령에 사용합니다.

```bash
git add practice.txt
git diff --cached
```

`git diff --cached`가 보여 주는 변경만 작성자와 검토자의 근거가 됩니다. 편집기에 수정 내용이 보여도 스테이지하지 않았다면 이 입력에는 포함되지 않습니다.

### 5~15분: 작성자 실행

Claude Code에서 `/commit-message`를 실행합니다. 또는 “스테이지된 변경으로 커밋 메시지 초안을 만들어 줘. 커밋은 하지 마”라고 요청합니다. `_workspace/commit-draft.md`를 열어 초안이 staged diff의 범위를 빠짐없이 설명하는지 확인합니다.

### 15~25분: 검토와 수정

`_workspace/review-report.md`에서 판정과 근거를 읽습니다. `REDO`라면 수정 지시가 구체적인지 보고, 수정 후에는 새 초안을 다시 검토합니다. 이전 보고서를 새 초안의 승인 근거로 재사용하지 않습니다.

### 25~30분: 세 결과 비교

최종 `git diff --cached`, `commit-draft.md`, `review-report.md`를 함께 봅니다. 세 자료가 같은 변경을 설명해야 합니다. `PASS`라는 단어가 있다는 이유만으로 검토가 끝난 것은 아닙니다. 커밋은 사람이 별도로 판단합니다.

실습 후 본인이 만든 `practice.txt`를 스테이징 해제하고 삭제할 수 있습니다. 로컬에서만 쓰는 `.claude/settings.local.json`은 권한 설정 파일이므로 공개 저장소에 추가하지 마세요.

## 대조 자료

같은 폴더의 [`claude_code_tips_NO-HARNESS.md`](claude_code_tips_NO-HARNESS.md)는 하네스 없이 작성된 Claude Code 팁 문서입니다. `CLAUDE.md`, 계획, 권한, 스킬, 훅, MCP에 관한 조언을 담고 있습니다. 실습 프로젝트와 주제가 다르므로 두 파일의 문장 품질을 비교해 하네스 효과를 측정하는 자료로 보기는 어렵습니다. 이 문서는 “일반적인 사용 팁”과 “특정 작업을 실행·검증하는 구성”의 차이를 살펴보는 대조 자료입니다.

## 현재 예시에서 발견할 수 있는 불일치

저장소에 포함된 산출물은 학습용 예시이며, 한 번의 최신 실행 결과가 아닙니다.

- 현재 `commit-draft.md`는 하네스 전체 추가를 설명하지만, `review-report.md`는 README만 설명한 다른 초안을 `REDO`로 판단합니다. 두 파일을 같은 실행의 결과로 보면 안 됩니다.
- `CLAUDE.md`는 `type(scope): subject` 형식을 요구하지만 현재 초안 제목 `feat: ...`에는 scope가 없습니다.
- 검토자 파일은 두 번 `REDO` 뒤 `PASS`로 종료하라고 하지만, 스킬은 재시도 한도 뒤 수동 검토를 권합니다. 이 규칙을 실행 전에 정리해야 검증 실패가 자동 통과로 바뀌지 않습니다.

이 불일치를 알아차리는 것도 실습입니다. 하네스가 잘 작동하는지는 설정 파일의 존재가 아니라 **입력과 산출물의 일치, 판정의 근거, 안전한 종료**로 확인합니다.

## 설계 관점: 누가, 어떻게, 언제

“에이전트는 누가, 스킬은 어떻게, 조율은 언제·누구와”라는 구분은 책임을 나눠 생각하는 데 유용합니다. Claude Code가 정한 공식 3계층 이름은 아닙니다.[1]

- **누가:** 작성자와 검토자의 역할, 판단 범위, 도구.
- **어떻게:** 제목·본문 기준과 검토 절차.
- **언제·누구와:** 스테이지 확인 후 작성자를 부르고, 작성 뒤 검토자를 부르며, `REDO`면 다시 작성시키는 흐름.

모든 작업을 한 에이전트에 넣으면 역할이 넓어져 검토가 빠지기 쉽고, 절차를 여러 파일에 중복하면 수정 시 기준이 어긋납니다. 반대로 너무 작은 일을 나누면 파일과 실행 비용만 늘어납니다. **분리가 반복 작업, 누락, 문맥 부담을 실제로 줄일 때만** 추가하세요.

## 에이전트 파일을 읽는 질문

역할 정의는 설정 모음보다 작업 계약에 가깝습니다. 실습 파일을 읽으며 다음을 확인해 보세요.

1. **핵심 역할:** 무엇을 맡고, 무엇은 하지 않는가?
2. **작업 원칙:** 증거가 부족하거나 기준이 충돌하면 어떻게 판단하는가?
3. **입출력:** 무엇을 읽고 어디에 어떤 형식으로 쓰는가?
4. **팀 통신:** 다음 역할이 무엇을 받아 어떤 행동을 하는가?
5. **오류 처리:** 입력이 없거나 재시도가 끝나면 어떻게 멈추는가?
6. **협업 순서:** 누가 먼저 실행되고 다음 단계는 무엇인가?
7. **자체 점검:** 제출 전에 어떤 기준을 확인하는가?

프론트매터의 `description`은 호출 상황, `tools`는 사용 도구, `model`은 모델 선택을 설명합니다. `name`은 고유 식별자이며 파일명과 같아야 하는 것은 아닙니다. 모델 필드를 생략했을 때의 선택 순서도 설정에 따라 달라지므로, 무조건 부모 모델을 상속한다고 단정하지 마세요.[2]
