# 스킬로 이슈부터 리뷰 반영까지: task-keeper 실습기

> 작은 FastAPI 앱 `task-keeper`의 N+1 쿼리 버그 하나를 두고, 이슈 생성부터 커밋, PR, 리뷰, 리뷰 반영까지의 흐름을 프로젝트 스킬 여섯 개로 쪼개 만들고 실제로 돌려 본 기록입니다.

- 실습 날짜: 2026-11-08
- 실습 저장소: [goodsosbva/task-keeper](https://github.com/goodsosbva/task-keeper) (이슈 [#1](https://github.com/goodsosbva/task-keeper/issues/1), PR [#2](https://github.com/goodsosbva/task-keeper/pull/2))
- 도구: Claude Code, `gh` CLI

## 1. 왜 스킬로 쪼갰나

같은 버그를 처리해도 "이슈 써 줘", "커밋해 줘", "PR 올려 줘"를 매번 프롬프트로 설명하면 결과가 그때그때 달라집니다. 제목 접두사가 빠지거나, 이슈 연결을 잊거나, 승인 없이 push하는 식입니다.

그래서 반복되는 절차를 **스킬**로 고정했습니다. 스킬 하나는 하나의 일을 맡고, 아래 세 가지를 문서로 정해 둡니다.

- **절차**: 어떤 명령을 어떤 순서로 실행하는가
- **형식**: 결과물(이슈, 커밋 메시지, PR 본문, 리뷰)이 어떤 모양인가 → `resources/`의 템플릿
- **멈추는 지점**: 어디서 사람의 승인을 받는가

## 2. 만든 스킬

```
.claude/skills/
├── create-issue/       # 요청 → 이슈
│   └── resources/issue_templates.md
├── git-commit/         # 변경사항 → 컨벤션 커밋
├── create-pr/          # 브랜치 → PR
│   └── resources/pr_template.md
├── review-pr/          # PR → 체크리스트 리뷰
│   └── resources/review_checklist.md
├── apply-pr-review/    # 리뷰 코멘트 → 코드 반영 + 답글
│   └── resources/reply_templates.md
└── commit-and-pr/      # git-commit + create-pr 연결
```

| 스킬 | 입력 | 출력 | 승인 지점 |
| --- | --- | --- | --- |
| `create-issue` | 자연어 요청 | `[Bug]`/`[Feature]`/`[Improvement]` 이슈, 라벨 | 이슈 내용 확인 후 생성 |
| `git-commit` | 작업 트리 변경 | `<type>(<scope>): <subject>` 한국어 커밋 | 커밋 명령 실행 시 |
| `create-pr` | 현재 브랜치 | 템플릿 PR, `Closes #N` 연결 | PR 내용 확인 후 생성 |
| `review-pr` | PR 번호 | 🔴/🟡/🟢 심각도별 리뷰 | GitHub 게시 전 |
| `apply-pr-review` | PR 번호 | 반영 커밋, 코멘트별 답글 | 반영 계획 확인 후 |
| `commit-and-pr` | 작업 트리 변경 | 커밋 + PR | 커밋 시, PR 생성 시 |

`create-issue`와 `git-commit`은 미리 준비된 스킬이고, 나머지 네 개는 이번 실습에서 직접 만들었습니다. 스킬별 설명은 [`wiki/skills/`](skills)에 있습니다.

### 만들면서 정한 원칙

- **템플릿은 `resources/`로 분리합니다.** `SKILL.md`에는 절차만 두고, 결과물 모양은 템플릿 파일에서 읽게 했습니다. 형식을 바꿀 때 절차를 건드리지 않아도 됩니다.
- **스킬끼리는 규칙을 복사하지 않고 호출합니다.** `commit-and-pr`은 커밋 규칙과 PR 템플릿을 다시 쓰지 않고, `git-commit`과 `create-pr`을 차례로 부르기만 합니다. `create-pr`의 제목 규칙도 `git-commit`의 type 목록을 그대로 따릅니다.
- **되돌리기 어려운 일 앞에서 멈춥니다.** 이슈와 PR 생성, GitHub 게시, push 앞에 승인 단계를 두었습니다. force push와 `main` 직접 push는 금지했습니다.
- **확인하지 못한 것은 확인하지 못했다고 씁니다.** 리뷰와 답글 템플릿에 "확인 필요"와 "실행하지 못함"을 쓰는 자리를 만들었습니다.

## 3. 실제로 돌린 흐름

```
create-issue ──▶ (수정) ──▶ git-commit ──▶ create-pr ──▶ review-pr ──▶ apply-pr-review
   이슈 #1                    커밋           PR #2         리뷰 게시      반영 계획 수립
```

### 3-1. `create-issue`: 증상 → 원인까지 담은 이슈

요청은 "할 일 목록 조회가 느림. 할 일이 많을 때 GET /tasks 응답이 오래 걸림" 한 줄이었습니다. 스킬은 이 문장만으로 이슈를 쓰지 않고, 먼저 코드를 읽어 원인을 찾았습니다.

- `list_tasks()`가 `db.query(Task).all()`만 실행하고, `Task.tags`는 `lazy="select"`라서 직렬화할 때 할 일마다 태그 쿼리가 따로 나갑니다. (N+1)
- 그래서 유형은 **bug**, 제목은 `[Bug] 할 일이 많을 때 GET /tasks 응답이 느림 (태그 N+1 쿼리)`로 정했습니다.
- 재현 방법에 `SQLALCHEMY_ECHO=1`로 쿼리를 확인하는 단계를 넣고, 측정값처럼 모르는 정보는 `TODO: 추가 정보 필요`로 남겼습니다.

**막힌 곳 두 군데**

| 문제 | 처리 |
| --- | --- |
| `needs-triage` 라벨이 저장소에 없음 | 스킬 5단계(라벨 확인 및 생성)대로 `gh label create` |
| 저장소의 Issues 기능이 꺼져 있어 생성 거부 | 저장소 설정 변경이라 바로 하지 않고 승인을 받은 뒤 `gh repo edit --enable-issues` |

### 3-2. `git-commit`: 성격별로 커밋 나누기

스킬과 위키 문서를 커밋할 때 `chore(skills)`와 `docs(wiki)` 두 커밋으로 나눴습니다. 스킬의 "가장 중요한 변경으로 type 결정" 규칙을 따르되, 성격이 확실히 다르면 나누는 쪽을 택했습니다.

여기서 **git 사용자 정보가 설정되지 않아** 커밋이 거부됐습니다. 전역 설정은 건드리지 않고 `git -c user.name=... -c user.email=...`로 이번 커밋에만 작성자를 지정했습니다.

### 3-3. `create-pr`: 요청과 실제 상태가 다를 때

"방금 커밋한 N+1 수정을 PR로 올려라"라는 요청을 받고 스킬 2단계(base 대비 모든 커밋 확인)를 실행해 보니, **브랜치에 N+1 수정 커밋이 없었습니다.** 커밋된 것은 스킬과 위키뿐이었습니다.

요청을 그대로 따랐다면 버그 수정 없는 "fix" PR이 올라갔을 것입니다. 실제로는 이 사실을 먼저 알리고, 수정을 만든 뒤 PR을 올렸습니다.

- 수정: `db.query(Task).options(selectinload(Task.tags)).all()`
- 회귀 테스트: `GET /tasks`의 쿼리 수가 2회인지 세는 테스트 추가
- 결과: [PR #2](https://github.com/goodsosbva/task-keeper/pull/2), `Closes #1`로 이슈 연결 (`closingIssuesReferences: [1]`로 확인)

**검증하면서 막힌 곳**

로컬 인터프리터가 **Python 3.14.0rc2**(정식판 이전 버전)여서, pydantic이 import 단계에서 `AssertionError`를 냈습니다. 수정 전 코드에서도 똑같이 실패하므로 이번 변경과는 관계가 없습니다. 정식판 Python을 받으려 했지만 환경에서 다운로드가 막혀 있었습니다.

그래서 pydantic을 거치지 않고 SQLAlchemy만으로 쿼리 수를 직접 셌습니다.

| | 할 일 50개일 때 쿼리 수 |
| --- | --- |
| 수정 전 | 51회 |
| 수정 후 | **2회** |

`pytest`를 돌리지 못했다는 사실은 PR 본문의 테스트 항목에 체크하지 않은 채로 남겼습니다.

### 3-4. `review-pr`: 자기 PR을 체크리스트로 리뷰

PR #2를 메타데이터, 코드 품질, 보안, 성능, 테스트 다섯 관점으로 점검했습니다. 판정은 💬 코멘트, Blocker는 없었습니다.

| 심각도 | 지적 |
| --- | --- |
| 🟡 Major | 새 테스트를 한 번도 실행하지 못함 |
| 🟡 Major | 같은 세션을 공유해서 수정 전에도 1+N이 아니라 1+(N-1)로 셀 수 있음 → `expire_all()` 필요 |
| 🟡 Major | PR에 관계없는 커밋 2개가 섞여 있음 |
| 🟢 Minor | README의 "알려진 버그" 설명이 이제 맞지 않음, models 주석, 테스트 안 import, 페이지네이션은 후속 과제 |

자기 PR이라 approve나 request-changes는 할 수 없어서 `gh pr review --comment`로 게시했습니다. 전문은 [`wiki/reviews/pr-2.md`](reviews/pr-2.md)에 있습니다.

### 3-5. `apply-pr-review`: 리뷰를 무조건 따르지 않기

처음 `/apply-pr-review 2`를 실행했을 때 PR에는 **코멘트가 하나도 없었습니다.** 앞의 리뷰가 로컬 파일로만 있었기 때문입니다. 스킬은 그대로 끝내지 않고 "리뷰를 먼저 게시할지"를 물었고, 게시한 뒤 지적 7건을 분류했습니다.

| 분류 | 건수 | 예 |
| --- | --- | --- |
| ✅ 반영 | 4 | `expire_all()` 추가, import 위치, README·models 주석 갱신 |
| 💬 답변 | 1 | 테스트 미실행: 이 환경에서는 해결할 수 없음 |
| 🙅 반영 안 함 | 2 | PR 분리(force push 필요), 페이지네이션(범위 밖) |

반영 계획은 승인을 기다리는 상태로 실습을 마쳤습니다. 코드 수정과 답글은 아직 하지 않았습니다.

## 4. 배운 점

1. **스킬은 요청보다 실제 상태를 먼저 확인해야 합니다.** "방금 커밋한 수정"이 없었던 일처럼, 요청에 담긴 전제가 틀릴 수 있습니다. `create-pr`의 "base 대비 모든 커밋 확인" 단계가 없었다면 빈 PR이 올라갔을 것입니다.
2. **환경 문제는 스킬이 아니라 보고에서 다룹니다.** Issues 비활성화, git 사용자 미설정, rc 버전 Python은 모두 스킬 바깥의 문제였습니다. 스킬이 우회 방법을 모두 정해 둘 수는 없으므로, 대신 "멈추고 알린다"를 기본으로 두었습니다.
3. **승인 지점은 되돌리기 어려운 일 앞에 둡니다.** 이슈와 PR 생성, 저장소 설정 변경, 리뷰 게시는 지워도 알림과 기록이 남습니다. 반대로 로컬 파일 작성 같은 일에는 승인을 두지 않아 흐름이 끊기지 않게 했습니다.
4. **검증 못 한 것을 기록하는 자리가 필요합니다.** PR 템플릿의 테스트 체크박스와 리뷰의 "확인 필요" 표시 덕분에, 돌리지 못한 테스트가 통과한 것처럼 보이지 않았습니다.
5. **스킬 조합은 호출로 합니다.** `commit-and-pr`을 만들 때 규칙을 복사하지 않고 두 스킬을 부르게 하니, 커밋 규칙을 고쳐도 한 곳만 바꾸면 됩니다.
